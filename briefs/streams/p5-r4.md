# Stream brief - P5 R4 Security hardening

Phase 5. Items: `briefs/plan-phase-5.md` section "R4". Owner tag: `[owner:R4]`. Agent: `go-dev` (`model` per the item's
tier) for test and tool items; review items are dispatched as `code-reviewer` (`model: "sonnet"`), which reads code and writes
only the findings file named in the item (the parent commits it). R4 may start as fill once phase P4 has exited.

## Scope
Product-wide security hardening before v1: an inventory of every untrusted-input decoder and long fuzz campaigns on Linux CI
(FEAT-174); protocol reviews of SPAKE2 (RFC 9382) and pairing; adversarial tests for TLS pinning, local IPC, decode limits,
network surface and clipboard/log privacy; the Windows service/helper privilege review and ACL checks on a real install; the
path-safety audit (FEAT-095); govulncheck on every platform; the dependency licence audit with a generated notices file (D-27);
a provenance check; the threat model; and the full `qa/security-review.md` pass (FEAT-173).

## Owned paths
- `test/security/**`, `tools/licenses/**`, `packaging/release/THIRD_PARTY_NOTICES.txt` (generated), `.github/workflows/fuzz.yml`,
  `qa/security/**`, `qa/threat-model.md`, `qa/security-review-results.md`, `internal/**/testdata/fuzz/**` (corpora only),
  `internal/transfer/safepath/adversarial_test.go` (all new in P5 except the corpora and results file; appended to `ownership.md`
  by the parent in P5-R2-001)
- `qa/manual/p5-r4-*.md`
- Fix items appended by the parent (`P5-R4-101+`) list their own files in any package.

## Files to leave alone
Everything not in your item's `Files:` line; all plan files; production code (review and test items never change production code:
a failing adversarial test is a finding, reported in BLOCKED with the failing test, and the parent appends a fix item).

## Conventions (binding)
- Checklist: `qa/security-review.md` sections 1-9 are the acceptance criteria; every finding is reported as
  `file:line - defect - severity (critical|high|medium|low)`.
- Decisions: D-14 (SPAKE2 P-256, 6-digit code), D-27 (licences, clean room), D-36 (decode limits, fuzzing), D-41 (identity,
  key storage), D-42 (SPKI pinning via `VerifyConnection`), D-43 (TXT keys), D-44/D-45 (transfer integrity, safe writes), D-46
  (IPC), D-47 (service IPC), D-48 (logging redaction), D-57 (pairing TTL/attempts, caps), D-61 and D-121 (clipboard scope; concealed content is shared), D-62 (cut
  as copy), D-63/D-64 (service, helper, pre-login), D-70 (WoL), D-72 (update check).
- Risks: R-03, R-04, R-24, R-33, R-39, R-44 (status notes appended by the parent in P5-R4-020).
- `test/security` is a test-only package (`doc.go` holds the package doc). It needs `test/...` in `tools/coverage-exclude.txt`
  like `test/e2e` (P3 G5); if the exclude file lacks it, report BLOCKED so the parent records the decision and adds it.
- Tests use only exported APIs of production packages and the test hooks those packages already expose (endpoint overrides,
  fakes); a missing hook is BLOCKED, never added here. Tests must not bind the agent's real IPC endpoint or port (24860): the user may
  run an installed EdgeSync on the dev PC.
- Tests touching the real registry, services or another user account are not written here; those checks live in the manual ACL
  script (P5-R4-009).
- Fuzzing on the host only as smoke (`-fuzztime 30s`); long campaigns run in `fuzz.yml` on ubuntu-24.04.
- No em dashes or en dashes anywhere; use "-". Commit `<type>(<scope>): <description> [FEAT-NNN]`, body `Item: <id>`, no
  attribution trailers, never push.

## Item P5-R4-004
Planning consolidation: D-110 confirms the password-to-scalar derivation of the P1-C2-005 brief; review it against RFC 9382 instead of raising it as an open question.
Review `internal/spake2` against RFC 9382 (https://www.rfc-editor.org/rfc/rfc9382) and write `qa/security/spake2-review.md` with
one row per check: check, RFC section, evidence (`file:line` or test name), verdict, finding.
- Ciphersuite SPAKE2-P256-SHA256-HKDF-HMAC; M and N equal the RFC's P-256 constants byte for byte.
- `w` derivation from the code: RFC 9382 section 3.2 requires `w = MHF(pw) mod p`; record what is used. A non-memory-hard
  derivation is a question for the parent ("6-digit one-time code, 3 attempts, 120 s TTL: is an MHF required?"), not a silent pass.
- `x`, `y` uniform in [0, p) from crypto/rand; `pA = w*M + X`, `pB = w*N + Y`; cofactor h = 1 for P-256.
- Received shares decoded strictly (on-curve, not the identity, canonical encoding); failures abort without further output.
- Transcript TT exactly as RFC 9382 section 3.3 (each field length-prefixed with an 8-byte little-endian length; order A, B, pA, pB,
  K, w); `Ke || Ka = Hash(TT)`; `KcA || KcB = KDF(Ka, nil, "ConfirmationKeys" || AAD)`; `cA = MAC(KcA, TT)`, `cB = MAC(KcB, TT)`.
- A and B are the two peer IDs; AAD is the TLS exporter value (D-14, architecture 6.5).
- Confirmation MACs compared with `hmac.Equal`; keys used only after both confirmations; scalar operations through nistec.
- Every P-256 test vector from the RFC's appendix is reproduced by a test.

## Item P5-R4-005
Review `internal/pairing` (and its GUI/IPC triggers) and write `qa/security/pairing-review.md`:
- exporter label `EXPORTER-EdgeSync-pairing-v1`, 32 bytes, used as AAD; pairing on its own ALPN `edgesync-pair/1`;
- code generated with crypto/rand without modulo bias, 6 digits, TTL 120 s, 3 wrong attempts invalidate the code, attempts counted
  per code across connections (D-57);
- the code is shown only after a local user action (`ShowPairingCode`); the initiator cannot choose or learn it;
- no pin, name or MAC is stored before both confirmations verify; a failed attempt stores nothing;
- failure responses identical for "wrong code" and other errors as seen by the peer, and no timing difference beyond noise
  (inspect the code path; note any early return before the MAC check);
- limits on concurrent pairing sessions and handshake timeouts (D-57 5 s) against floods;
- unpair removes pins and closes live sessions (FEAT-128).

## Item P5-R4-009
`qa/manual/p5-r4-acl.md` in the `qa/manual/README.md` format. Machines: one Windows PC with the installer run (after P5-R1-M01),
an admin account and a standard account (the script tells the user how to create a temporary standard account and remove it in
Cleanup). Steps:
1. Admin PowerShell: `Get-Acl "\\.\pipe\<service pipe>" | Format-List` and the same for the helper pipe (names from W2 code; the agent
   fills them in); expected owners and ACEs per D-47.
2. Standard user: connect to the service pipe with `[System.IO.Pipes.NamedPipeClientStream]`, write 16 bytes, expect the server to close
   the pipe; admin checks the service log for the rejected client entry.
3. `icacls "%ProgramData%\EdgeSync"`, `icacls "%ProgramData%\EdgeSync\identity"`, `icacls "%ProgramFiles%\EdgeSync"`.
4. Standard user: try to create a file in `%ProgramFiles%\EdgeSync` and in `%ProgramData%\EdgeSync` (both denied).
5. `sc.exe sdshow <service name>`: no ACE grants Users or Authenticated Users change-config, write-DAC or write-owner rights.
6. Second account logged in via fast user switching: try to open the first user's agent pipe `\\.\pipe\edgesync-agent-<SID>` (denied).
7. `reg query HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run` shows the quoted agent path.
Cleanup: remove the temporary account. Safety: nothing here changes EdgeSync state.
