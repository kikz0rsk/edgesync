# Stream brief - P3 G2 Machines, pairing, permissions and first-run wizard

Phase 3, parallel stream. Items: `briefs/plan-phase-3.md` section "G2". Owner tag: `[owner:G2]`.
Read first: `briefs/streams/p3-f.md` sections "Conventions", "GUI design" and "Spine gaps" (binding), then this brief.

## Scope
The Machines page (paired and discovered machines, rename, unpair, connect, wake, add/remove an address), the pairing
dialogs for both sides (D-14), the permissions and environment-checks model and page, and the first-run wizard
(D-18): role, pairing, OS permissions, Windows firewall check, GNOME tray-extension hint. FEAT-148, FEAT-149, FEAT-150,
FEAT-056, FEAT-068, FEAT-077, FEAT-130.

## Files you may touch
`gui/peers/**`, `gui/wizard/**`, `internal/i18n/locales/en/gui_machines.toml`; `cmd/edgesync/pages.go` only in the
registration items with the claim. Read, never edit: `internal/ipc`, `internal/pairing`, `gui/state`, `gui/shell`,
`gui/widgets`, `gui/theme`.

## Dependencies
IPC (through `gui/state`): `ListPeers`, `ListDiscovered`, `AddManualPeer`, `RemoveManualPeer`, `StartPairing`,
`SubmitPairingCode`, `ShowPairingCode`, `CancelPairing`, `Unpair`, `RenamePeer`, `SetRole`, `Connect`, `Disconnect`,

`PeersChanged`, `DiscoveryChanged`, `PairingProgress`, `PermissionStateChanged`, `EnvironmentChanged`,
`StatusChanged`, `ConfigChanged`. Event variant names follow the P3-F-002 decision ("Spine gaps" 8); all mapping from
IPC types to view-model states lives in one function per view model so the rest of the code never sees IPC types.

## Decisions
D-03 (roles), D-14 and D-57 (6 digits, TTL 120 s, 3 attempts), D-15 (discovery + manual), D-18 (wizard content), D-21,
D-39/D-02 (permissions per OS), D-43 (default port 24860), D-59 (Busy), plus the P3-F decisions (first-run state,
environment checks, manual-address removal).

## Security rules for this stream (checked by P3-G2-R02)
- The pairing code exists only inside the pairing view model (as `[]byte`), the dialog's display and the IPC call.
  It is zeroed when the dialog closes or the flow ends. It is never passed to `slog`, never part of an op name, never
  in an error text, never written to the clipboard by EdgeSync, never placed in a semantic description other than the
  visible code field (screen readers may read it: that is the point of showing it).
- Op names: `"pairing.start"`, `"pairing.submit"`, `"pairing.show"`, `"pairing.cancel"` (constants).

## Screen: Machines (design)
- Header: title "Machines", [Pair with this computer] (opens the responder dialog; shows this machine's code),
  [Add by address].
- Section "Paired machines": rows (56 dp) with name, short ID (`xxxx-xxxx`, mono), badge (Connected = Online,
  Connecting, Offline, Busy with "Controlled by <server>"), "In layout" or "Not in layout", last seen (relative time)
  when offline; row actions (buttons, Tab-reachable): server role: [Connect]/[Disconnect], [Show in layout]; both
  roles: [Send files] (when connected), [Wake] (when offline and a MAC is known), [Rename], [Unpair] (danger).
  Client role: no Connect/Disconnect/Show in layout; header note "This computer is a client. The server connects to it."
- Section "Discovered on the network": rows with name, address, role, short ID, source label "Added by address" for
  manual entries; actions [Pair]; manual entries also [Remove].
- Empty states: paired: "No paired machines yet. Pair a machine found on your network, or add one by address.";
  discovered: "Searching the network..." with spinner for the first 5 s after the page is first shown, then "No
  EdgeSync machines found. Make sure EdgeSync runs on the other computer and both are on the same network, or add it
  by address." with [Add by address].
- Dialogs: Rename (TextField, validation via `format.ValidateMachineName`, Enter saves, Escape cancels); Unpair
  confirm (danger: "Unpair <name>? It can no longer connect until you pair it again."); Add by address (host field +
  port NumberField default 24860, validation via `format.ValidateHost`/`ValidatePort`, inline errors, [Add]).
- Per-row request errors appear under the row in Danger text until the next action on that row.

## Screen: Pairing dialogs (design)
- Initiator ("Pair with <name>"): text "Enter the 6-digit code shown on <name>."; six single-digit boxes (40 sp mono)
  backed by one hidden editor (typing fills boxes; Backspace moves back; paste of "123456", "123 456" or "123-456"
  fills all); "Expires in m:ss"; "Attempts left: n" after the first wrong code; [Pair] (enabled at 6 digits; Enter);
  [Cancel] (Escape). States: Starting (spinner "Connecting to <name>..."), EnterCode, Verifying (spinner), Succeeded
  ("Paired with <name>." [Done]), Failed (reason text + [Try again] which restarts the flow, [Close]).
- Responder ("Pair with this computer"): text "Enter this code on the other computer:"; the code as "123 456" in
  40 sp mono; "Expires in m:ss"; when a peer joins: "<name> is entering the code"; after a wrong attempt: "Wrong code
  entered. n attempts left."; Succeeded ("Paired with <name>."), Expired ("The code expired." + [Show new code]),
  Failed (reason) ; [Cancel]/[Close].
- An incoming pairing attempt while no responder dialog is open (event `codeShown` generated by the agent) opens the
  responder dialog automatically on any page.
- Failure texts per reason: tooManyAttempts "Too many wrong codes. Start pairing again.", expired "The code expired.
  Start pairing again.", cancelledLocal (dialog just closes), cancelledRemote "Pairing was cancelled on <name>.",
  unreachable "Could not reach <name>: <detail>", rejected "<name> rejected the pairing.", protocol "Pairing failed:
  <detail>".

## Screen: Permissions and checks (design, hidden route `permissions`)
Title "Permissions and checks". Section "Permissions" (rows from `GetPermissions`): label per kind (Accessibility -
"Accessibility (control this Mac)"; Input Monitoring - "Input Monitoring (read keyboard and mouse)"; Portal
InputCapture - "Input capture (share this computer's keyboard and mouse)"; Portal RemoteDesktop - "Remote input (be
controlled by the server)"; Portal Clipboard - "Clipboard access"), state badge (Granted/Missing), detail text, [Grant]
(RequestPermission) with guidance "Approve the request, or open System Settings > Privacy & Security and enable
EdgeSync." on macOS. Section "Checks" (from `GetEnvironmentChecks`, `unsupported` hidden): firewall ok "Windows
Firewall allows EdgeSync."; problem "Windows Firewall may block EdgeSync. Allow EdgeSync through Windows Defender
Firewall (the installer adds this rule)." + [Check again]; tray problem on GNOME "No tray icon: install the GNOME
extension 'AppIndicator and KStatusNotifierItem Support'." + [Check again]. All good: "Everything is set up."

## Screen: First-run wizard (design, route `wizard`, full window)
Card 640 dp wide, centred; header "Set up EdgeSync" + "Step n of m" (m counts only the steps that are shown); footer
[Back] [Skip] [Next]/[Finish].
1. Welcome: what EdgeSync does (three short lines). Next only.
2. Role: RadioGroup "This computer's keyboard and mouse control the others (server)" / "This computer is controlled
   by another computer (client)". Next disabled until chosen; Next calls `SetRole` (pending spinner; error stays on the
   step).
3. Pairing: server - the discovered list with [Pair] per row (initiator dialog) and "Paired so far: n"; client - the
   responder panel inline ("Enter this code on the server"). [Skip] allowed ("You can pair later on the Machines page").
4. Permissions: the permission rows; auto-skipped when the list is empty (Windows); [Skip] asks for confirmation
   ("EdgeSync cannot share input until these permissions are granted. Skip anyway?").
5. Checks: the environment checks; auto-skipped when none applies (all unsupported); [Skip] allowed.
6. Done: summary (role, paired machines, open problems) and [Finish]: sets `first_run_completed = true` and
   `wizard_step = 0`; the shell gate opens `layout` (server) or `machines` (client).
Each Next persists `wizard_step` through `UpdateConfig`; on start the wizard resumes at the persisted step (clamped to
the steps that apply). Back allowed on steps 2-5.

Offline, Busy); BusyWith string; InLayout bool; CanWake bool; LastSeen time.Time; Err string }`, `type

## Item P3-G2-004
`gui/peers/vm/pairing.go` (sonnet item):
- `type Pairing struct` with `Kind` (Initiator, Responder) and `Step` (Starting, EnterCode, Verifying, ShowingCode,
  PeerJoined, Succeeded, Failed, Expired, Closed).
- Initiator: `StartInitiator(d, target)` -> op `"pairing.start"`; `AwaitingCode` event -> EnterCode with `ExpiresAt`,
  `AttemptsLeft = 3`; `SetCode(input string)` keeps only digits (spaces and dashes removed, max 6); `Submit(d)` only with
  6 digits -> Verifying, op `"pairing.submit"`; `AttemptFailed(n)` -> EnterCode, digits cleared, `AttemptsLeft = n`,
  message; `Failed(reason)` -> Failed with the reason text; `Succeeded` -> Succeeded; countdown reaches 0 -> Failed
  (expired) locally even before an agent event; `Cancel(d)` -> op `"pairing.cancel"` -> Closed.
- Responder: `StartResponder(d)` -> op `"pairing.show"`; `CodeShown(code, expiresAt)` -> ShowingCode; `PeerJoined(name)`;
  `AttemptFailed(n)`; `Succeeded`; `Expired` -> Expired with `NewCode(d)` restarting.
- `Present(now)` returns texts (countdown via `format.Countdown`, code grouped "123 456") and flags; `Close()` zeroes
  the code bytes.
- `MapEvent(ev)` converts every `PairingProgress` variant to the calls above (`TestPairing_EventMappingAllVariants`
  covers each variant). `TestPairing_CodeNeverLogged` installs a capturing `slog` handler as the default and as the
  store logger, runs both flows, and asserts the code digits never appear.

## Item P3-G2-011
D-112, D-113. `gui/peers/vm/prelogin.go`: the view model for the sign-in screen switch and the Send Ctrl+Alt+Del row action. Inputs: `GetPreloginAccess` (IPC, P3-G5-020: `supported`, `reason`, `detail`, `allowedPeerIds`), the peer rows of P3-G2-001 and the peer facts (`os`, `capabilities.secureDesktop`, online, role) from `ListPeers`.
- The switch exists only on a Windows machine whose access query reports `supported`; reasons `noService` and `serviceError` show a disabled switch with an explanation, `notWindows` hides it.
- `SetPreloginAccess(ctx, peerID, on)` builds the argument list (`allow-prelogin <peer-id> --name "<display name>"` or `allow-prelogin --remove <peer-id>`) and runs it through an `Elevator` interface (`Elevate(ctx, args []string) (exitCode int, err error)`; the Windows implementation is P3-G2-012, tests use a fake). Exit 0: refresh `GetPreloginAccess`; exit 3 (not elevated: the user declined the UAC prompt or is not an administrator): keep the old state with the message "Administrator permission is required"; exit 4 or 1: show the message for the code. The state is never changed optimistically.
- Unpair: `Unpair(peer)` for a peer in `allowedPeerIds` first runs the removal; if it fails or is declined the unpair is cancelled with the reason (the entry must not outlive the pairing).
- Send Ctrl+Alt+Del: a row action available only in the server role for connected peers with `os == "windows"` and `secureDesktop`; it calls the IPC request `SendCtrlAltDel{peer}` and shows the text of an `ErrorInfo` on failure.
Keys `gui.machines.prelogin.*` and `gui.machines.sendcad.*` (the catalogue file is edited by P3-G2-012).
